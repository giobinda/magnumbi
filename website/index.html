Why it stays consistent

There is no “UI version” and “code version” of your setup to drift apart. There's one, and every path leads to it.

  • The UI is an API client. It has no private shortcuts, so anything you can click, you can automate.
  • Dashboards are YAML underneath. Edit one in the designer and its YAML view updates; paste YAML and the designer shows it. Same object, two views.
  • One set of rules. A change is checked the same way whether it comes from a click, a file or a script — invalid changes are refused, never half-applied.
  • Definitions live in code. Models (what “revenue” means) come from reviewed YAML only, so metrics can't be quietly changed in a browser.
  • Full history. Every dashboard save is kept with its author, whichever way it was made.

Blazing fast. Isolated by design.

Magnum BI runs on ScramDB: each organisation gets its own ScramDB instance holding its dashboards and its query cache. Answers come back fast, and one tenant's data never sits next to another's.

~1 sa month of NYC taxi trips, from 208 million rows
~2 sa blend joining 3.5 million trips with weather from another database

Results as real tables

Cached results are stored as typed tables in ScramDB, not blobs. The same tables power blends, so joining data across engines is fast too.

One cache per tenant

Each organisation's cache lives in its own ScramDB instance. If one is slow or unreachable, only that organisation notices — sign-in and every other tenant keep working.

Never leaks across people

Cache entries include each person's row filters, so a cached answer is only shared between people who'd see exactly the same rows anyway.

Caching is opt-in per model (cache: 15m), so live data stays live where it matters. Admins can see and clear their cache at any time. How the cache works →

Deployed by your agent in minutes

Magnum BI is made to be set up by coding agents. It ships as one Docker image with a Compose file and a Helm chart, the repository has an AGENTS.md with every command and rule, and every setting is an environment variable or a YAML file.

Everything you need, nothing you don't

Magnum BI keeps business intelligence simple: one place to define what your numbers mean, and friendly tools to look at them.

Models & dashboards as YAML

Drag-and-drop explorer

Drop fields onto shelves to build a chart, pick a chart type, and save it to a dashboard. No SQL required — though you can always see it.

Period comparison

Compare with the previous period, the previous year, or any date you choose. Every tile shows the change, and you can sort by it.

One-line embedding

Put a live dashboard in your own app or intranet with a single HTML tag, filters included.

Public and guest links

Share a dashboard with anyone, from a cache that protects your data warehouse; or with guests, by link and password for up to 14 days, limited to the data you choose.

Secure by default

Roles, row filters, sealed credentials, strict security headers, and read-only queries. Every rule is enforced on the server.

Modern sign-in

Passkeys, authenticator codes, Google, and each organisation's own single sign-on (Entra ID, Okta, Keycloak…), with policies that can require two factors.

Your brand colours

How it works

Three steps from raw table to a dashboard people actually use.

Connect your data

Add a connection to PostgreSQL, ScramDB, BigQuery or DuckDB (Parquet, CSV, Iceberg files and more). Test it before you save.

Describe it once

Write a small model: which columns are dimensions, which are measures, and how to drill. That's your single source of truth.

Explore & share

Build charts in the explorer, arrange them on a dashboard, and share or embed it. Viewers just pick filters and dates.

A model is just a short file

Models say what your numbers mean. Dashboards, the explorer and embeds all use them, so “revenue” means the same thing everywhere.

  • Time grains like sold_at:month out of the box
  • Reuse a model with extends: and add fields
  • Caching with one line: cache: 15m
  • Validation with make check before you deploy
project/models/sales.yaml 
name: sales
connection: warehouse
table: sample_sales
dimensions:
  - {name: sold_at, type: time}
  - {name: region}
  - {name: store}
measures:
  - {name: revenue, type: sum, sql: amount, format: currency}
  - {name: transactions, type: count}
hierarchies:
  location: [region, store]   # drill path

Why Magnum BI?

Light to run

One small Docker image (about 150 MB) serves the API and the UI on one URL: docker compose up on a laptop, or the Helm chart on Kubernetes. It keeps no state of its own, so you can run as many copies as you like.

Fast where it counts

Queries are compiled to native SQL for each engine, and an opt-in, tenant-isolated cache on ScramDB answers repeat questions instantly. See the numbers.

Version-controlled

Models, dashboards, blends and themes are plain YAML in a project/ folder. Review them in pull requests like any other code.

Yours to own

Self-host it on your own infrastructure. Your data stays in your databases; Magnum BI only reads it.

Case file · Behind the name

Why “Magnum”?

The name is a nod to Magnum, P.I., the TV series in which Tom Selleck plays Thomas Magnum, a private investigator in an aloha shirt solving cases around Hawaiʻi in a red Ferrari. Magnum P.I. investigated people; Magnum BI investigates your data. The job is the same: follow the clues, ask the right questions, and never take a number at face value.

Clue #1 · The red Ferrari

The accent colour on every button and link: a red Ferrari 308, cooling to coral after dark.

Clue #2 · The aloha shirt

Lagoon, hibiscus, pineapple, ocean, plumeria, palm, sunset and orchid: the chart palette, every colour checked for contrast.

Clue #3 · Sand & Pacific night

The app's default themes, Aloha and Aloha night, follow your system's light or dark setting, just like this site.
